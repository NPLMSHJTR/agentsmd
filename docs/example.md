# A worked example

A real before-and-after, using the repository this tool lives in. The point is to
show what a generated file looks like, what a bad hand-written file looks like,
and what the verifier says about each.

---

## The starting point

Imagine a TypeScript project with this shape:

```
demo/
├── package.json          # scripts: { test: "vitest run" }, devDeps: vitest
├── pnpm-lock.yaml
├── .eslintrc.json
├── .prettierrc
├── src/
├── tests/
└── scripts/
    └── codegen.ts        # first line: // DO NOT EDIT. Generated.
```

No `AGENTS.md` exists. Every session, the agent spends its first turns working
out that this is pnpm and not npm, that tests run through vitest, and that
`scripts/codegen.ts` should not be touched.

---

## What `agentsmd generate` produces

```markdown
# AGENTS.md

<!-- Generated by agentsmd from files on disk. Every line below is traceable to
a file in this repository. Run `agentsmd verify` after changing the build. -->

This file tells a coding agent how this specific repository works, so it does
not have to rediscover the setup on every task.

## Project

- Primary ecosystem: **node**
- Package manager: **pnpm**

## Commands

These are the exact commands. Do not substitute a global tool for the
project-local one.

- Test: `pnpm test`
- Lint: `pnpm exec eslint .`
- Format: `pnpm exec prettier --check .`

## Layout

Top-level directories, excluding tooling directories: `scripts/`, `src/`,
`tests/`

## Do not edit

These files declare themselves generated. A change here is overwritten on the
next build:

- `scripts/codegen.ts`

## Continuous integration

The build that must pass: `.github/workflows`

## Not covered by this file

Detection reads files. It cannot know the following, and neither can an agent
until someone writes it down:

- Which conventions are enforced in review but not by a linter
- Which parts of the codebase are fragile, deprecated, or off limits
- What the definition of done is for this project
- Which commands are safe to run against production data
- Domain vocabulary that a newcomer would misread

Add those by hand. Keep them short and specific: an instruction an agent cannot
follow is worse than no instruction, because it looks like guidance and costs a
turn to disprove.
```

Notice three things.

**It writes `pnpm exec eslint .`, not `eslint`.** A bare tool name is not a
command. The generated file spells out the invocation the repository would
actually use, which is why it passes its own verifier.

**`src/` and `tests/` are listed without explanation.** The tool knows the
directories exist. It does not know what belongs in them, so it does not claim to.

**The last section is not filler.** It is the honest boundary of what a program
can determine, and it is where the human work starts.

## Filling in the human part

The generated file is a draft. A finished one adds the four or five things only a
person knows:

```markdown
## Conventions not covered by the linter

- Every module in `src/` exports through `index.ts`. Importing a deep path is a
  review failure even though it compiles.
- `src/legacy/` is being deleted in Q2. Do not add code there; open an issue
  instead.

## Definition of done

A change is done when `pnpm test` passes and `pnpm exec eslint .` reports
nothing. There is no separate staging step.

## Domain vocabulary

A "batch" is a group of jobs submitted together and is not the same as a
"run", which is one attempt at a batch. The distinction matters in
`src/scheduler.ts`.
```

Every line here is specific enough that an agent can act on it and a reviewer can
check it. That is the standard the verifier enforces with AG006.

## What a bad file looks like, and what verify says

This is the file most repositories end up with. It was written once, correctly,
eighteen months ago.

```markdown
# AGENTS.md

## Guidelines

Please write clean, readable code and follow best practices. Be careful when
making changes.

## Commands

- Install: `npm install`
- Test: `yarn test`
- Build: `npm run build`

## Structure

The main logic lives in `src/main.ts`. Tests are in `tests/`.

## Instructions

Think step by step before making changes. Do not hallucinate APIs.
```

Running `agentsmd verify` against it, in a repository that migrated from npm to
pnpm and renamed `src/main.ts` to `src/index.ts`:

```console
$ agentsmd verify

E AGENTS.md — 5 error, 3 warning
    error AG003 `npm install` uses npm, but this repository uses pnpm
         A wrong package manager produces a lockfile in the wrong format.
    error AG003 `yarn test` uses yarn, but this repository uses pnpm
    error AG002 `src/main.ts` is referenced but does not exist
         This is the most common way an AGENTS.md goes stale.
    error AG001 `npm run build` is presented as a command, but `npm` ... 
    warn  AG006 line reads as advice an agent cannot verify: 'Please write
          clean, readable code and follow best practices...'
         Replace it with a checkable fact or delete it.
    warn  AG006 line reads as advice an agent cannot verify: 'Think step by
          step before making changes.'
    warn  AG007 the repository has a test command but the file never mentions
          tests
         Add `pnpm test`.
```

Every finding is real. The file tells an agent to install with npm in a pnpm
repository, run tests with yarn, read a file that does not exist, and be careful
— and it never mentions the command that actually runs the tests.

The three "be careful" lines are the most instructive. They are not errors in any
sense. They are the reason the file feels complete while containing nothing an
agent can execute.

## The habit this is meant to create

The verifier only helps if it runs. Two places it belongs:

**In CI**, so a build-file change cannot silently break the instructions:

```yaml
- run: agentsmd verify . --strict
```

**Before a release**, when the commands in the file have probably drifted:

```bash
agentsmd verify . && agentsmd generate . --force
```

The second command is worth looking at closely: it regenerates from scratch
rather than patching. For the parts detection covers, that is the cheapest way to
be correct. The human sections have to be re-added, which is annoying enough that
most people check the file instead — and checking is the behaviour that keeps it
true.

## A note on scope

This example uses a Node project because the failure modes are easy to see. The
same structure applies to Python (`pytest`, `ruff`), Rust (`cargo test`,
`cargo clippy`) and Go (`go test ./...`, `golangci-lint run`). Detection covers
all five; the human sections differ by project, which is exactly why they cannot
be generated.
